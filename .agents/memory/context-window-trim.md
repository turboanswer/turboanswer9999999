---
name: context-window-trim
description: Why chat 400s on long conversations and how the router trims history to fit the model context window.
---
Long conversations (or a few large pasted messages) can exceed a model's context window and make Azure return `HTTP 400: maximum context length is N tokens, your messages resulted in M tokens` — this fails even a trivial "hi" because the bloat is the HISTORY, not the new message. Free tier (gpt-4o-mini) is the smallest at 128k, so it hits this first.

**Rule:** never cap chat history by TURN COUNT alone — cap by an estimated TOKEN budget against the resolved model's context window. The chat route trimming by `.slice(-20)` turns was insufficient because a handful of large messages blow past 128k.

**Why:** prod free-tier chat 400'd at 164k tokens > 128k; the public-OpenAI fallback then masked it with a misleading 401. Capping by tokens at the model chokepoint fixes it for every route at once.

**Estimate UNDER-counts — trimming "to budget" is not enough by itself.** The chars/4 estimate under-counts real Azure tokens for code/JSON/non-English, so a payload the trimmer believed was ~122k (budget = contextLimit − reserve ≈ 95% of window) was really ~160k → STILL a 400 even though the trim ran. Two changes were needed: (1) estimate divisor 4 → 3.5 (slight over-count) and cap input at ~70% of the window (`min(contextLimit − reserve, contextLimit*0.70*factor)`), not ~95%; (2) the real guarantee — a retry-on-context-400 loop.

**The guarantee is the retry, not the estimate.** `callDirect`/`callDirectStream` loop over `factors = [1, 0.6, 0.4]`, calling `fitMessagesToContext(messages, r, opts, factor)` per attempt; on a 400 whose body matches `isContextLengthError(...)` they re-trim harder and retry, else report+break. Any estimation error is absorbed by shrinking the budget and retrying — don't chase a "perfect" token count.

**How to apply:**
- The guard lives in `direct-router.ts` (`fitMessagesToContext`, now called PER-ATTEMPT inside the retry loop of both `callDirect` and `callDirectStream`, not once up top). Each resolved model carries a `contextLimit` (gpt-4o-mini 128k, gpt-4.1 1M, gpt-5.x 256k).
- Retries use an ABSOLUTE token ceiling, not just a fraction of the model's window. Module-level `CTX_RETRY_ATTEMPTS = [{factor:1},{factor:0.6,absCap:90k},{factor:0.4,absCap:45k}]`; `fitMessagesToContext(..., factor, absCap)` budgets `min(contextLimit−reserve, contextLimit*0.70*factor, absCap)`. **Why:** budget was a fraction of each model's CONFIGURED `contextLimit` (pro gpt-4.1=1M, gpt-5.x=256k); if a configured limit exceeds the REAL Azure deployment window, even 0.4×0.7×1M=280k stays over a real 128k → still 400 on "every model". 90k/45k are safe for the smallest real window we serve (128k), so retries converge regardless of `contextLimit` accuracy.
- The Responses-API path (enterprise gpt-5-pro / codex) ALSO retries now: `azureResponsesNonStream` takes an `onCtxError` callback that fires on a context-length 400; the responses branch in `callDirect`/`callDirectStream` loops `CTX_RETRY_ATTEMPTS`. No duplicate output risk — those models are non-streamed and emitted as one chunk only after success.
- It keeps all system messages + the most recent turn and drops OLDEST turns first; the last-resort pass then truncates the CURRENTLY LARGEST message (system OR conversation) repeatedly until it fits — system prompts are cut only here, after larger messages, so a giant pasted user msg is trimmed before the system prompt. `truncateContentText` now also handles ARRAY/vision content (truncate text blocks; drop oldest images keeping ≥1). Loop skips an unshrinkable message (a lone image) and keeps draining the rest (`frozen` set, `guard<100`).
- Streaming retry is SAFE from duplicate output: a context-length 400 is rejected at request time (`res.ok` false) before any SSE chunk; once `consumeOpenAIStream` emits deltas it returns non-empty `acc` and the loop does NOT retry. Public/non-stream fallbacks receive FITTED messages (raw-history was a latent bug).
- NOT a "any payload mathematically can't 400" guarantee — describe it as fixing long-history / oversized-text overflow across all tiers. Truly pathological image-only payloads (one retained image per many system messages) are the only theoretical residual; doesn't occur with this app's single-string system prompt.

**Verified e2e** against the real Azure endpoint: huge-history 242 msgs/~1.2M est tok → trimmed to 19 → HTTP 200 normal answer; giant-system (single ~257k-tok system msg) → truncated to ~89.5k → returned an answer; all `ctx400=false`. An unrelated image-format 400 from the gpt-4o-mini vision deployment fires for BOTH truncated and untrimmed small messages, so it is NOT this code. Prod deploy is via git push → GitHub Actions → Azure App Service (NOT Replit Deploy); see prod-deploy-pipeline.md.
